# 11 浏览器扩展 ↔ Claude Code 本地桥接方法论

> 把"浏览器里选中一个对象 → 交给本机 Claude Code 处理 → 结果回显到扩展"这条链路跑通的通用方法论。以「自检」功能为实战案例，沉淀可复用的架构与避坑清单。

---

## 一、要解决的本质问题

浏览器扩展想借用本机 Claude Code 的能力（审查、生成、分析…），但两者天然隔离：

- 扩展跑在浏览器沙箱里，**够不到本机的 `claude` CLI**。
- Claude Code 是被动的——**不会自己盯着某处等活干**。
- API Key 不能塞进扩展（代码公开，会被盗刷）。

桥接的任务：在"浏览器扩展"和"本机 Claude Code"之间架一座通信的桥，让选中的对象数据流过去、结果流回来。

---

## 二、最终架构（一句话）

**扩展 → 本机 HTTP 服务 → `claude -p` 无状态调用 → 结构化 JSON 回流。**

```
选中元素 → 扩展面板点按钮
  → content script（不受 SW 回收）
  → 每次发"秒回的短请求"给 background（两段式：发起 + 轮询）
  → background 用扩展 host 权限 fetch 本机服务（不受页面 CSP）
  → 本机 HTTP 服务收到 → spawn `claude -p`（读一份自包含 prompt）→ 审查
  → 服务返回结构化 JSON → 逐层回流 → 面板渲染
```

三个部件：
1. **前端**：扩展面板 UI（tab、按钮、结果渲染）。
2. **通信桥**：content script ↔ background ↔ 本机 HTTP 服务。
3. **后端**：本机 HTTP 服务（`server.mjs`）+ 自包含指令（`audit-prompt.md`）。

---

## 三、为什么是"HTTP 服务 + claude -p"，而不是别的

| 方案 | 结论 | 原因 |
|---|---|---|
| 扩展直接调 Claude API | ✗ | Key 不能进扩展；且卖家中转 token 不是标准 API Key，程序无法调用 |
| `/loop` 让 Claude Code 盯文件夹 | ✗ | 每次轮询都调一次模型，烧 token、占性能，空闲也烧 |
| 文件夹当信箱 + 本地脚本 watch | △ | 可行但比 HTTP 绕：要轮询文件、处理时序 |
| **本机 HTTP 服务 + `claude -p`** | ✓ | 事件驱动（有请求才调 claude）、空闲零开销、实时、实现简单 |

**关键认知：审查/处理交给 `claude -p`（headless 单次调用），它是独立进程**——
- 和终端的交互式 Claude Code 窗口无关，开不开都行。
- 消耗的是本机 CC 源的额度（跟随 `~/.claude/settings.json`，切源即切）。
- 无状态：**不加载任何 skill**。要复用某套方法论，必须把规则"抄"成一份自包含 prompt 喂给它。

---

## 四、MV3 扩展的两个致命坑（必踩，必须绕）

这是整条链路最花时间的地方。MV3（Manifest V3）扩展有两个硬约束，长任务（审查要 50~60s）会同时撞上：

### 坑 1：页面 CSP 挡住 content script 直连 localhost
- content script 的 `fetch` 受**所在页面的 CSP（connect-src）**约束。
- 很多站点（尤其企业站）不允许连 `127.0.0.1`，直连会被浏览器静默挡回。
- **解法：fetch 改走 background service worker**——它用扩展的 `<all_urls>` host 权限，**不受页面 CSP 约束**。

### 坑 2：service worker 空闲 ~30s 被回收，长任务响应丢失
- MV3 的 background 是 service worker，空闲约 30 秒被 Chrome 杀掉。
- 审查要 50~60s，若 background 在一个长 `fetch` 上等待，**中途 worker 被杀 → sendResponse 永不触发 → 前端拿不到结果**。
- 试过的两种 fixes：
  - 定时调 chrome API 保活 → 不够可靠。
  - port 长连接（`chrome.runtime.connect`）保活 → 理论可行但时序坑多（连接建立/断开竞争）。
- **最稳解法：两段式短轮询**——把"一个长请求"拆成"多个秒回的短请求"：
  1. content script 让 background 发起审查 → 服务**立即返回 taskId**（后台异步跑）。
  2. content script **每 3 秒**让 background 查一次结果 → 服务秒回 `running` / `done`。
  3. 每次 background 只需存活 <1 秒，**永远不会撞上 30 秒回收**。

---

## 五、数据流转的层级对齐（易错点）

数据穿过 4 层（panel → content → background → 服务），**每一层的数据结构要对齐**，最隐蔽的 bug 就藏在这。

实战翻车案例：服务返回 `{ok:true, result:{issues:[...]}}`，但 content script 回传给 panel 时只传了 `result`（即 `{issues:[...]}`），而 panel 却按 `resp.ok` 判断成功——`{issues}` 没有 `.ok` 字段，于是明明成功却显示"失败"。

**教训：**
- 明确每一层"传出去的是什么、收进来的按什么判断"，画一张数据结构流转图。
- 判断成功用**业务字段**（如"有没有 issues 数组"），别依赖可能在传递中被剥掉的包装字段（`ok`）。

## 六、后端服务的工程要点

1. **零依赖**：纯 node（`http` + `child_process`），别引外部包，方便分享。
2. **claude 路径要通用探测**：launchd/服务环境 PATH 很干净，靠 PATH 找 `claude` 会 ENOENT。要按常见安装位置逐个探测 + `which` 兜底，**不硬编码用户名/路径**（否则别人机器上用不了）。
3. **给子进程补 PATH + HOME**：`claude` 内部还要调 node/git。
4. **结构化输出要防脏**：模型偶尔在 JSON 字符串值里写英文双引号破坏 JSON。双保险：① prompt 里硬约束"值内禁用英文引号，用「」"；② 服务端解析失败**自动重试一次**。
5. **常驻**：用 launchd（macOS）设开机自启 + 崩溃自动重启（KeepAlive），用户无需手动开服务。
6. **CORS 放开**：服务响应加 `Access-Control-Allow-Origin: *`。

---

## 七、性能与成本（回答"会不会很重"）

- **不用 `/loop`**：那是每几秒调一次模型，烧 token、占性能。
- **事件驱动**：本机服务只有真收到请求才 spawn 一次 `claude`，**空闲时零开销**（HTTP 服务空转几乎不耗 CPU）。
- **短轮询的轮询本身很轻**：查结果是本机内存里的 Map 命中，秒回，不调模型。
- 烧钱的只有"真正审查那一次"，和手动用一次 Claude Code 同价。

---

## 八、可复用性 / 分享（拿来就用）

- **前后端合并进扩展包**：后端（HTTP 服务 + prompt + 一键安装脚本）放进扩展目录，分享一个包搞定。
- **扩展与服务只靠 HTTP 端口（127.0.0.1:PORT）连接**，不靠文件路径——所以后端目录放哪都行。
- **一键安装脚本**：探测 node/claude 路径 → 动态生成 launchd 配置（用本机真实路径）→ 启动 → 探活。把"配三样东西"变成"跑一个脚本"。
- **launchd 配置不打包**：由安装脚本按每台机器路径动态生成，避免硬编码。

---

## 九、通用配方（迁移到任何"扩展借用 Claude Code"的场景）

1. 扩展选中对象 → 采集数据（outerHTML / 截图 / 上下文）。
2. content script 发起 + 轮询（两段式短请求），**不做长等待**。
3. background 用 host 权限 fetch 本机服务（**绕 CSP**）。
4. 本机零依赖 HTTP 服务：`/start` 立即返回 taskId + 后台 `claude -p`，`/result` 轮询取。
5. `claude -p` 读一份**自包含 prompt**（要复用某方法论就把它抄进来），强约束结构化 JSON 输出 + 解析失败重试。
6. 结果逐层回流，**判断成功用业务字段**。
7. launchd 常驻 + 一键安装脚本，前后端合并进扩展包分享。

## 十、本次实战的遗留优化点（备忘）

- 当前审查用的是 `audit-prompt.md`（skill 方法论的**浓缩版**），**没直接用 skill 本体**。想提升准确度：把 skill 的更多规则（Step 0 上下文对齐、9 层细则、严重程度判定）搬进 audit-prompt.md，或让服务真正去读 skill 文件。
- 换端口（默认 8765 冲突时）需同步改扩展里的 `127.0.0.1:8765`，目前是两处硬编码，可抽成配置。
